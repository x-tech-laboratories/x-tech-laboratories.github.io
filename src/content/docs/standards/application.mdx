How X-Tech applications are built. Every app follows it where possible, so the shared code in X-Libs and the shared styling in Halon serve all of them.

## Purpose and scope

* Every X-Tech app is written in TypeScript on Node with React.
* The web app is the primary target. Desktop and mobile wrap the same React page, so every target shows the same X-Libs widgets.
* One widget set, one agent and server stack and one toolchain are shared across apps. This is what lets X-Libs be used in full.
* The standard covers new apps and rewrites. An existing app moves over in the order given under Current state.
* Exceptions stay as they are until they are rewritten:
  * a Python app with no UI of its own (a daemon, an experiment, a training pipeline);
  * a LightDM greeter or other component whose host fixes its language (web-greeter);
  * a library or tool with no UI and no server (RoboBuddy, ai-readiness) still follows the toolchain and code conventions, and nothing else.
* A reason to deviate is a hard platform limit: the host only runs another language, a required library exists only for another language, or the app must run where Node cannot. Taste, familiarity and a smaller bundle are not reasons.
* A deviation is written down in the app's `README.md` with the limit that forces it.

## Stack per target

| Target          | Stack                                                                                  |
| --------------- | -------------------------------------------------------------------------------------- |
| Web app         | React page bundled by Vite, served by a Fastify server                                 |
| Desktop app     | Electron built with electron-vite, wrapping the same React UI                          |
| Mobile app      | Capacitor, wrapping the same React UI                                                  |
| CLI and agent   | Node script in TypeScript, built on the X-Libs `agent` modules                         |

Versions floor:

* Node 24 or newer; `"engines": { "node": ">=24" }` in `package.json`.
* TypeScript 7 or newer, strict.
* React 19 or newer.
* Vite 8 or newer.
* Fastify 5 or newer, with `@fastify/cookie`, `@fastify/session`, `@fastify/rate-limit`, `@fastify/static` and `@fastify/websocket` as the app needs them.
* Electron and electron-vite at the current major.
* Capacitor at the current major.
* `oxlint` for linting, `vitest` for tests.

Rules per target:

* The web, desktop and mobile apps share one `src/web` React tree. The desktop app loads it in the renderer and reaches the main process through a preload bridge.
* A desktop app that also ships as a web app runs the same Fastify server, either in the main process or as the web build.
* A mobile app loads the built `src/web` page in Capacitor and reaches the server over its API. Phone features such as the camera or notifications come through Capacitor plugins, wrapped in X-Libs when a second app needs them.
* A page works at phone width, through the X-Libs `Shell` and the widgets' phone layouts.
* Every app's sidebar ends in the same foot, drawn by the `Shell` and pinned to the sidebar's bottom while the rows above it scroll: the app's own rows, such as sync state, then the theme, then the signed-in user and Sign out, then Settings, last. None of these sits in the top bar, which holds only the brand and the app's tools.
* The server owns the app's storage, a JSON store or SQLite as the data needs; the browser page and the agent reach it only through the server.
* A desktop or mobile app that must work offline keeps its own SQLite copy and syncs it with the server through the X-Libs sync modules; its page reaches that copy only through the app's bridge.
* A server or an agent never shells out when a Node API does the job.

Data and migrations (an app with a SQLite store):

* The store is code in `src/shared` that runs unchanged on the server, in Electron's main process and in a phone's page, on the X-Libs `SqlDatabase`. It imports nothing from the DOM or from `node:` modules.
* An app with several parts, such as a workout log and a food diary, keeps each in its own folder under `src/shared/<feature>/` with its own tables, calls and settings, and a list of features names them. Each feature's migrations are its own, run through `migrate(database, steps, { owner })`, so features change without renumbering each other's steps.
* Tables are written once as a Drizzle schema (`schema.ts`, with the builders X-Libs re-exports). `drizzle-kit generate` writes each change as a migration, `x-libs-bundle-migrations` turns the migration folders into an `index.ts` the server, the desktop app and the phone's page all import, and `synced_tables(...)` reads the sync list, parents first, from the schema's primary keys. A released migration is never edited, only followed by a new one; data a migration only moves is made with `drizzle-kit generate --custom`.
* Rows have ids that every device can make on its own, such as a UUID, and never an auto-incrementing key, since two devices would reuse it.
* Queries go through `drizzle_of(database)` from X-Libs. Raw SQL is for what Drizzle does not express, such as `COLLATE NOCASE` or ordering by `rowid`.
* The browser page imports only types from the stores, plus a small file that names the calls and the page's api, so the stores, their migrations and Drizzle stay out of the bundle a server sends. A page that needs a setting's default reads it from a plain settings file with no imports, or from the server, never from a store.
* A call that only reads is named `list_`, `get_`, `search_`, `lookup_` or `export_`, and any other call announces a change to the other pages and devices.

## APIs and MCP

Other programs reach an app's data as well as its own page does, so it can be scripted, linked to other tools and used by an AI client. Wherever an app has a server:

* Every call the page makes is open to other programs through the server's API, behind the same sign-in. A program sends a token made on the user's account page as a bearer header.
* Every call is described once in an X-Libs `api_spec`: what it does in plain words, and a JSON Schema for each argument. The spec is typed against the app's method table, so a call without one fails to compile.
* The server serves the same calls three ways from that one spec:
  * the app's own API, which takes the arguments as a list in order or by name as a JSON object;
  * `GET /api/openapi.json`, an OpenAPI 3.1 document from `openapi_document`;
  * `/api/mcp`, every call as an MCP tool over streamable HTTP from X-Libs `server/mcp`, which wraps the official SDK (`@modelcontextprotocol/server`).
* A call that only reads is named so (`list_`, `get_`, `search_` and the like) and is marked read-only to MCP clients. A change made through the API or MCP reaches open pages and devices as if made in the app.
* Values cross the API in the units the app stores, and the spec says which.
* What the API returns leaves out keys and passwords for other services.
* An app without a server, such as a desktop-only app, offers MCP where its host allows, or writes down in its `README.md` why it cannot.

## Accounts and signing in

Every app whose users sign in does it the same way, so a user meets one sign-in page, one account page and one set of words in every app. The modules are `server/account_store` and `server/account_sign_in` on the server, and `web/accounts`, `web/react/sign_in` and `web/react/accounts` on the page.

Who signs in:

* Users have a name and password. The users in the accounts file (`<APP>_PASSWORD_HASH_FILE`, one `name:hash` line each, written by `npm run hash-password`) are admins, and the page cannot change their role or password. Admins add every other user on the Users page.
* Users, sessions and tokens are kept in the app's own SQLite database, so a restart signs no one out.
* Roles are the app's own, ordered from least to most able, with the last role managing users. An app that grants more than everything or nothing gives its own access rules and an editor for them.
* Single sign-on through an OpenID Connect provider (`<APP>_OIDC_*`) and a trusted reverse proxy's user header are optional. Both sign in only users an admin has added.
* An app does not use one shared secret for browsers or devices.

The sign-in page:

* `SignInForm` asks for the user name and password. Once the password is right, and only if the user has turned on a second factor, it asks for the code from an authenticator app or a recovery code.
* A "Keep me signed in" box is unticked by default. Unticked, the session ends when the browser closes; ticked, it lasts until the user or an admin signs it out, or the cookie is cleared. The server can bound both lengths (`session_seconds`, `remembered_seconds`).
* After five wrong tries from one address for one name, that pair waits a few minutes.

Words: the app says "Sign in" and "Sign out", never "Log in" or "Log out", and "Keep me signed in". Refusals read "Wrong name or password." and "Too many tries; wait a few minutes."

Account pages:

* The sidebar's foot shows the signed-in user's name, linked to Your account, with a Sign out button beside it, between the theme and Settings (the `Shell`'s `user`, `user_href`, `on_logout` and `settings`).
* Your account (`AccountView`) lets each user change their password, turn the second factor on or off, see where they are signed in and sign any of those out, and make and revoke tokens.
* Users (`UsersView`), shown only to admins, adds, edits and removes users, resets a second factor and signs a user out everywhere. Changing a user's role, access or password signs them out everywhere.

Devices and programs:

* A desktop or phone app that syncs signs in from `SyncSettings` with the same name and password, and gets a token of its own, named for the device. Stop syncing gives the token back.
* A program uses a token made on Your account, read-only unless the user unticks that, sent as `Authorization: Bearer <token>`. A token cannot change the account it belongs to.

## Sync, backups and history

An app's data is kept the same way in every app, so users get the same safety everywhere and X-Libs holds one copy of the code. The modules are named in the [X-Libs README](https://github.com/x-tech-laboratories/X-Libs#readme).

Sync:

* An app whose data lives on more than one device, such as a desktop or phone app with its own copy and a server, syncs through X-Libs: `create_sync_engine` on the app's store, `register_sync_routes` on the server and `create_sync_client` on each device. An app does not write its own sync, sync its database file through a file-sync tool, or use a CRDT library.
* The newest write of each value wins. The first time a device connects, the user chooses which copy wins, and the other is backed up before it is replaced.
* A device keeps the server's address and token through `file_sync_storage` on the desktop and `local_sync_storage` on a phone, never in the synced data. Settings that belong to one device are listed in the engine's `local_keys` or `local_columns`.
* The device's bridge answers the `SyncDeviceMethods` through `sync_device_methods`. Its settings page shows `SyncSettings` under a section called "Sync", where the device signs in with the user's name and password and asks before one copy replaces the other. A browser shows no sync section, since it is already on the server.
* A server whose https certificate the device refuses, such as a home server's self-signed one, is reached only after the user trusts it, through X-Libs' certificates. The dialog shows the certificate and what is wrong with it, and trusts that exact certificate for that host alone. The desktop keeps them with `create_certificate_trust`, honours them with `trust_in_session`, and sends sync through `trusting_fetch`. A phone uses `phone_certificates`, whose plugin lets the WebView through. The page passes `certificates` to `SyncSettings`, places `SyncCertificatePrompt` once, and lists `TrustedCertificates` in the Sync section. An app never turns certificate checks off, trusts a whole authority for every host, or writes its own certificate handling.

Backups:

* Every app that keeps data of its own backs it up: an SQLite store through `sqlite_backups`, any other store through `backups` with a store of its own. Backups are named by `backup_naming` after the time they were taken.
* Daily backups are on by default and keep the last 14 (`default_backup_schedule`). `keep_backing_up` takes them while the app runs. Backups made by hand are always kept. The schedule is a setting of the device, never synced.
* A backup is taken before anything replaces the data: a restore, a sync that takes the server's copy, a replace of the server's data, and a schema upgrade.
* A restore backs up the current data first, so it can itself be undone. After a restore, sync forgets its history (`after_restore: engine.forget_history`), and the user chooses again which copy wins.
* Where backups go: beside the database in the desktop app's profile folder, in a folder the user picks on a phone, and in the data folder of a server. The settings page shows `BackupSettings` under a section called "Backups", through the `BackupMethods` calls.

History:

* An app whose users make and edit items, such as tasks, transactions or workouts, keeps a history of them through `create_history`. Every change to an item is a version; any version can be restored, and a deleted item can be brought back with what was deleted along with it.
* The history watches every table that changes an item, the item's tags and links included. `record` runs after every write, however the write was made, the API and MCP included.
* The versions table syncs like any other (`history.synced_table`), and `history.forget_touched` is the sync engine's `after_apply`, so each version is recorded once, by the device that made it.
* Versions older than a set number of days are pruned, keeping each item's newest. The number of days is a setting.
* The page shows an item's history from the item itself, and the latest changes to every item on a page of their own, through the `history_methods` calls.

Where these do not fit, such as an app whose data is a cache of files or of another service, or a log that is never edited, the app's `README.md` says which it leaves out and why.

## Shared code

Code that two apps need lives in `@x-tech-laboratories/x-libs` (repo X-Libs). Styling lives in `@x-tech-laboratories/halon` (repo X-Themes). An app imports it and does not write its own copy.

Comes from X-Libs:

* Agents and long runs: `agent/*` and `server/agents/*` (`AgentHub`, `LongRuns`, `TaskRunner`, the key login and the protocol).
* Accounts and signing in: `server/account_store`, `server/account_sign_in`, `server/passwords`, `server/hash_password`, `server/totp`, `server/oidc`, and on the page `web/accounts`, `web/react/sign_in` and `web/react/accounts`; `agent/keys` for agent keys.
* SQLite and sync: `sql` (the connection type, transactions and per-owner migrations), `drizzle` for typed queries, and `sync_engine`, `sync_client` and `server/sync_routes` for keeping devices alike.
* Durations, sizes, times and formatting: `durations` and `web/format`. They wrap `parse-duration`, `Intl` and `pretty-bytes`; an app does not parse or format these itself.
* The web shell and widgets: `Shell`, layout, badges, controls, tables, toasts, dialogs, menus, split panes and the `use_resource` states.
* The hash router and the theme choice: `web/router` and `web/theme`.
* Describing the API and serving it to other programs: `api_spec` and `server/mcp`.

Comes from Halon:

* The tokens (`halon-tokens.css`) and the widget stylesheets (`halon.css`). An app imports them once and does not restyle a widget.

Adding to X-Libs:

* Porting an app runs both ways: a port also pulls into X-Libs every feature the app has that X-Libs lacks and another app could use, so all the apps gain it.
* Code that a second app needs moves into X-Libs, in a branch of X-Libs, and the app then imports it. The app does not keep a fork or a patched copy.
* A module is one file per concern under a subpath: `server/...`, `agent/...`, `web/...`, `<name>.ts` at the top for plain helpers.
* A module imports nothing from an app.
* A widget has a test beside its behaviour and a short entry in the X-Libs README table.
* A widget that needs a style gets it in Halon first.

Widgets and external libraries:

* Every UI feature that two apps need lives in X-Libs.
* X-Libs either writes the feature or wraps an external library.
* An external library is chosen only when it matches or exceeds the in-house behaviour feature by feature.
* The library is wrapped inside X-Libs. An app never imports it directly.
* X-Libs adds only its own improvements and the parts the library lacks on top: Halon markup, accessibility, phone layout and keyboard paths.
* The comparison that justified the choice is written in the X-Libs README row or the module header.
* Current choices:
  * `@tanstack/react-table` (headless) holds the table state inside the X-Libs `DataTable`.
  * Drizzle ORM (pinned to 1.0.0-rc.5 until 1.0 is stable) types SQLite queries and writes migrations inside the X-Libs `drizzle` module; an app writes its schema with the builders X-Libs re-exports and never imports `drizzle-orm`.
  * Shortcuts, menus, trees, dates, the Electron bridge and the window helpers are in-house.
  * Rejected: tinykeys and hotkeys-js, electron-window-state, dnd-kit and pragmatic-drag-and-drop for now, and CRDT libraries.

Versioning:

* X-Libs and Halon use semver. A breaking change raises the major version and states what to change in the commit message.
* `react`, `react-dom`, `fastify` and `@fastify/websocket` are `peerDependencies` of X-Libs, marked optional in `peerDependenciesMeta`, so a CLI or an agent installs neither.
* An app depends on a caret range of X-Libs and Halon and installs its own single copy of React and Fastify.

## Plugins

An app that can be extended does it the same way in every app, so a plugin author meets one manifest, one set of extension points and one settings page. The modules are `plugins`, `plugin_folder` and `server/plugin_files` for any side of the app, and `web/plugin_imports` and `web/react/plugins` on the page. They are named in the [X-Libs README](https://github.com/x-tech-laboratories/X-Libs#readme).

What a plugin is:

* A plugin is a plain object: a manifest (`id`, `name`, semver `version`, the `app` and `app_versions` it is meant for, the plugins it `requires` with their versions, and its `settings` fields) and a `start(context)`. An app does not write its own plugin manager, registry or manifest.
* The app says once, in its shared types, what plugins may reach: its `hooks`, `providers`, `slots` and `services`. Plugins are written with `define_plugin<TheApp'sApi>`.
* A plugin adds hooks, providers, commands, slot contents and settings only through its context. Everything it added is taken back when it stops, is turned off or fails to start. A plugin does not reach into the app any other way.
* Hooks are the app's own events, such as `task.created`, called with `host.call`. A throwing hook is reported through `on_error` and the rest still run, so a hook does not veto an action; the app reads a flag on the hook's argument for that. Providers are the app's named choices, such as X-Stream's `video_source`; the app picks one by id with `host.provider`.
* Plugins start after the plugins they require. A plugin meant for another app or app version is refused, and one whose requirement is missing waits and starts when it arrives.

Where plugins come from:

* Bundled plugins are added with `host.add` and need nothing else. An app's own features that others could replace, such as a video source or an importer, are written as bundled plugins.
* Folder plugins are optional. Each subfolder of the app's plugins folder holds a `package.json` with `"type": "module"` and `"x-plugin": { "server": "dist/server.js", "web": "dist/web.js" }`, one bundled ESM file per side. The server, agent and Electron main process read them with `load_plugin_folder`; the page gets its side from `register_plugin_files` and `load_plugin_modules`, after `share_modules` has handed over the page's React.
* A web folder plugin is imported from a `data:` URL, so the page's Content-Security-Policy has to allow `data:` scripts for it.
* Folder plugins run with the app's full rights and are not sandboxed. The app's README says so, and only plugins the user chose to install are loaded. An app that wants third-party plugins from strangers asks first, since that needs a sandbox X-Libs does not have.

In the page:

* The settings page shows `PluginSettings` under a section called "Plugins": each plugin's name, version, state and, when it cannot run, why, with an On switch and its settings fields. On and off and the settings are kept through `json_plugin_storage` in the app's own store, so they survive a restart.
* Plugin parts of the page are drawn with `PluginSlot`, which leaves out a part that throws without taking the page down. Plugin commands are bound with `use_plugin_shortcuts` and listed in menus with `plugin_menu_items`.
* The page draws after `host.start()` has finished, since pages ask for what plugins provide as they mount.

## Repository layout and scripts

Reference layout (X-Backups):

```
src/
  server/    Fastify app, config, stores, schedulers, main.ts
  web/       React page: index.html, main.tsx, views/, app.css
  agent/     the agent that runs on managed hosts: main.ts
  shared/    types and protocol used by more than one of the above
tests/       one *.test.ts per behaviour, mirroring src/
docs/        written documentation
.github/workflows/ci.yml
.oxlintrc.json  (optional)
nix/         package.nix, module.nix, agent-module.nix
flake.nix
shell.nix
config.example.json
tsconfig.json  tsconfig.server.json  tsconfig.web.json
vite.config.ts
```

* A desktop app adds `src/main` and `src/preload` and builds with `electron.vite.config.ts`. A mobile app adds `capacitor.config.json` and the generated `android/` project. A target the app does not have gets no folder.
* `tsconfig.json` holds `references` only. Each target has its own `tsconfig.<target>.json`: `server` and `agent` use the Node types; `web` uses `jsx: react-jsx`, the `DOM` lib and `vite/client`.
* `config.example.json` is the complete, working default config. `dev:server` runs against it.
* `nix/` holds the package and the NixOS modules. `flake.nix` exposes the package, the modules and a dev shell. `shell.nix` serves `nix-shell`.
* `docs/` holds anything longer than the README.

Script names, the same in every app:

| Script        | Does                                                       |
| ------------- | ---------------------------------------------------------- |
| `dev:server`  | `node --watch src/server/main.ts` against the example config |
| `dev:web`     | `vite`                                                     |
| `dev`         | `electron-vite dev` (desktop apps)                         |
| `build`       | `tsc -b && vite build`                                     |
| `start`       | `NODE_ENV=production node src/server/main.ts`              |
| `typecheck`   | `tsc -b --noEmit` or per target (optional)                 |
| `test`        | `vitest run`                                               |
| `lint`        | `oxlint`                                                   |
| `db:generate` | `drizzle-kit generate` for every feature, then `x-libs-bundle-migrations` (apps with a Drizzle store) |

An app adds its own commands (`hash-password`, `seed`) beside these and does not rename them.

## Code conventions

* TypeScript strict, ESM only. `package.json` has no `"type": "commonjs"`.
* The shared base is `X-Libs/tsconfig.base.json`: `strict`, `allowImportingTsExtensions`, `verbatimModuleSyntax`, `erasableSyntaxOnly`, `moduleDetection: force`, and the unused-code and fallthrough checks. An app's configs set the same flags.
* Relative imports end in `.ts` or `.tsx`. Node runs the server's `.ts` files directly; the build rewrites the extensions for packages.
* `erasableSyntaxOnly` rules out `enum`, `namespace` and constructor parameter properties. Use unions, objects and plain fields.
* Type-only imports use `import type`.
* Names are snake_case: functions, variables, files. Types and React components are PascalCase.
* Comments are one plain line. A comment says what the code does not.
* Widgets are named exports. There are no default exports of widgets or components.
* No class hierarchies for UI. Components are functions; shared state is a hook or a small module.
* Tests live in `tests/` and are named for the behaviour they cover: `tests/scheduler.test.ts` for `src/server/scheduler.ts`. A change to behaviour changes a test in the same commit.
* Secrets never sit in the repo, in config examples or in logs. A config names a file that holds the secret.
* Licence: GPL-3.0-or-later in `package.json` and in `LICENSE`.
* Commits use Conventional Commits (`feat(web): ...`, `fix(agent): ...`, `refactor: ...`). A breaking change uses `!`. A commit made with a tool's help carries an `Assisted-by` trailer naming it.
* The dev environment is the Nix flake or shell. `nix-shell` gives Node and the tools the tests need.

## Testing and linting

* `vitest` is the test runner in every repo. `npm test` is `vitest run`.
* Tests live in `tests/` and are named for the behaviour: `tests/scheduler.test.ts`. A rendered component test is `tests/<widget>.test.tsx`.
* A rendered test starts with `// @vitest-environment jsdom` and uses `@testing-library/react` (`render`, `screen`, `fireEvent` or `user-event`). Queries go by role and text, never by class.
* Node code is tested without a DOM.
* Tests fix dates and clocks (`vi.useFakeTimers` or an explicit `now` argument), use no network, and keep files in temp dirs.
* Characterization tests come before a port or an extraction: pin the current behaviour of the module being moved, move it, then run the same tests against the new home.

What to test:

* Every exported function with a rule in it.
* Every widget's keyboard path and accessibility roles.
* Every wire message shape.
* Not tested: markup snapshots and styling.

Linting and types:

* `oxlint` is the linter in every repo. `npm run lint` is `oxlint`.
* A clean lint is a condition for landing.
* A rule override goes in `.oxlintrc.json` with a one-line reason each.
* `tsc -b` (or the repo's `typecheck` script) is part of `build` and runs in CI.

Where it runs:

* Local runs cover only the files changed. CI runs the whole suite.
* CI is one GitHub Actions workflow, `.github/workflows/ci.yml`, on push to `main` and on pull requests: Node 24, `npm ci`, `npm run build`, `npm test`, `npm run lint`. X-Libs carries it:

```yaml
name: CI

on:
  push:
    branches: [main]
  pull_request:
    branches: [main]

jobs:
  ci:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v7
      - uses: actions/setup-node@v7
        with:
          node-version: 24
          cache: npm
      - run: npm ci
      - run: npm run build
      - run: npm test
      - run: npm run lint
```

Dev dependencies every repo carries for this:

* `vitest`, `oxlint` and `typescript`.
* For repos with widgets, also `jsdom`, `@testing-library/react` and `@testing-library/dom`.

## Styling and branding

* Pages draw their look from Halon: `halon-tokens.css` for colours, spacing and type, `halon.css` for the widget styles. An app's own `app.css` holds layout only and uses the tokens, never raw colours.
* Light and dark themes come from the tokens and the `web/theme` choice. An app does not ship its own theme switch.
* Colours are the [Design Guidelines](/standards/design) scheme: Baby Blue `#0088ff` and white. Fonts are Rajdhani for headings and Noto Sans for text.
* Names follow the [Design Guidelines](/standards/design) naming scheme: `X-` and a hyphen, then a descriptive word (X-Backups, X-Nix). Where a hyphen is not allowed (package names, identifiers), the name is camel case (`XBackups`) or lower case with the hyphen kept (`x-backups`), as the platform allows.
* Logos come from the `logo` folder in the [branding folder](https://github.com/x-tech-laboratories/.github/tree/main/branding) of the organisation's `.github` repository.
* Every app has its own icon in the X-Tech style, as the [Design Guidelines](/standards/design#app-icons) set out: a glyph cut out of the X-Tech hexagon, drawn once as `resources/icon.svg`, with the desktop, Android and web icons generated from it.

## Checklist for a new app

* [ ] Name follows the [Design Guidelines](/standards/design) (`X-<Word>`).
* [ ] `resources/icon.svg` is an X-Tech style icon, and the desktop, Android and web icons are generated from it.
* [ ] Repo has `LICENSE` (GPL-3.0-or-later), `README.md`, `flake.nix`, `shell.nix`.
* [ ] `package.json`: `"engines": { "node": ">=24" }`, `"license": "GPL-3.0-or-later"`, ESM.
* [ ] Layout is `src/server|web|agent|shared` (or `src/main|preload|web` for desktop), plus `tests/`, `docs/`, `nix/`.
* [ ] `tsconfig.json` references one config per target, each with the strict flags from `tsconfig.base.json`.
* [ ] Scripts `dev:server`, `dev:web`, `build`, `start`, `test`, `lint` exist and use the standard commands.
* [ ] `config.example.json` runs the app as it stands.
* [ ] Depends on `@x-tech-laboratories/x-libs` and `@x-tech-laboratories/halon`; no re-implemented sign-in, agent, formatting, widget or theme code.
* [ ] Imports Halon's tokens and stylesheet once; `app.css` holds layout only.
* [ ] Signing in uses the X-Libs accounts (`register_accounts`, `SignInForm`, `AccountView`, `UsersView`) and says "Sign in" and "Sign out"; agents use the X-Libs agent modules.
* [ ] Every call has an `api_spec` entry, and the server offers `/api/openapi.json` and `/api/mcp`.
* [ ] Data on more than one device syncs through the X-Libs sync modules.
* [ ] A server with a self-signed or untrusted certificate is reached only after the user trusts it, through the X-Libs certificate modules.
* [ ] Data is backed up daily through the X-Libs backups, before every replace, with a Backups section in settings.
* [ ] Items users edit keep a history through `create_history`.
* [ ] An app that can be extended uses the X-Libs plugin host, with its bundled plugins, a Plugins section in settings and its trust note in the README.
* [ ] Tests exist for the behaviour that is written, and `oxlint` is clean.
* [ ] A CI workflow exists (`.github/workflows/ci.yml`).
* [ ] A rendered test exists for each widget the app adds.
* [ ] No app-level copy of an X-Libs widget.
* [ ] Commits are Conventional Commits.
* [ ] Any deviation from this document is written in the README with its reason.
